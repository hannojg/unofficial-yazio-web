The page’s public configuration supplies Apple client com.yazio-website.siwa and callback https://www.yazio.com/app/login. AppleID.auth uses a popup. Its success event supplies an identity token, which the page submits as jwt with grant_type=sign_in_with_apple to /api/auth/token. The response contains access_token and refresh_token. The website uses client_id 7_9236kdzucvnd624cklgz787kcvhjfch6sbdejgmdv8387fj7v. The refresh request uses the same official endpoint. There is no need to use an embedded mobile client secret in this implementation.

YAZIO's auth Pinia store uses redisPersist (BiXilQJ4.js), with accessToken, refreshToken, and loginMethod. The Nuxt app restores it when the account page loads and exposes window.useNuxtApp (bN-RGMk4.js); the Pinia plugin provides $pinia.state.value.auth (Pnq4E_Qq.js). A signed-in page can therefore skip /api/auth/token altogether. Although its persistence client advertises GET /api/store/{name}, GET /api/store/auth returned HTTP 404 in the live site; that unused route is not used by the extension.

The single connection flow reads the page's loaded auth store after Connect. A packaged MAIN-world script reads only those two token fields when asked. The isolated content script asks only after the worker confirms this is the tab opened for an active connection. It continues waiting on the same store for a new sign-in. The worker validates the session against /v22/user, refreshes an expired access token when needed, then persists it in chrome.storage.local restricted to TRUSTED_CONTEXTS. No token-response interception, REST-store alternative, hosted server, ChatGPT identity, encrypted server cookie, or shared encryption key is retained. Direct Chrome requests to the daily-summary endpoint returned HTTP 403 with error version_blocked, while account profile reads succeeded. The former server sent the Android user-agent above. With user approval, a declarativeNetRequestWithHostAccess rule now sets that header only on requests initiated by this extension to https://yzapi.yazio.com/v22/. The rule is installed before API operations begin. Website tabs and the official web refresh endpoint retain their normal headers.

API base: https://yzapi.yazio.com/v22
GET /user — account display / search parameters / validate session
GET /user/widgets/daily-summary?date=YYYY-MM-DD — energy, macros, water, and goals
GET /user/consumed-items?date=YYYY-MM-DD — products, recipe_portions, simple_products
GET /products/search?query=...&sex=...&countries=...&locales=... — food search
GET /products/{uuid} — product nutrients and base unit
GET /recipes/{uuid} — recipe name
POST /user/consumed-items — products array with UUID, product_id, amount, daytime, full local date-time, nullable serving fields
DELETE /user/consumed-items — JSON object with bucket name mapping to a SINGLE entry UUID string
POST /user/water-intake — array with date and absolute water_intake in millilitres
POST https://www.yazio.com/api/auth/token — refresh grant for the website client

Recents and water units — 28 October 2026
Android fz3.c fetches GET /v22/user/consumed-items/latest?limit=1..500. The response is a flat list of typed diary items (product, simple_product, recipe_portion), with local date-time and the logged amount. Android gv case 21 wraps this as consumedItems3 cached state; u65.f groups regular products by product ID and retains their newest logged item. The extension picker uses that same history endpoint, deduplicates regular foods by newest date-time, and shows up to 40 recent foods from all meals. Choosing one opens a portion review with its latest quantity prefilled. Recipe and quick-entry history are separate from the regular-food recents list.

The live endpoint requires authentication (anonymous probe: 401). Four automated recents tests verify ordering, deduplication, latest quantities, empty history, and error behavior. The original hosted picker was also verified live with the user's account.

Water correction: APK avj.WaterAmount names its numeric value mlValue, and WaterUnit defaults to Milliliter. The connected account's goal is 2000, representing 2 L. Previous research incorrectly described litres at the API boundary. The UI now divides the display by 1000; a 250 ml glass increments the raw amount by 250. The extension command accepts amountMl explicitly and forwards millilitres to YAZIO. No hydration data was changed while investigating.

Extension-only migration — 28 October 2026
Version 2.0.1 packages the React UI as index.html and a Manifest V3 background worker. It has no server build or hosted-app dependency. chrome.storage.local holds the session on this device, and chrome.storage.session holds the pending sign-in. Only extension dashboard pages can issue diary commands; the YAZIO content script can submit the saved web session from its paired tab. No externally_connectable or web_accessible_resources entry is needed. Chrome host permissions allow direct YAZIO requests without an app-side CORS proxy.

Activity budget and food portions — 28 October 2026
The daily-summary widget already includes activity in goals["energy.energy"] when consume_activity_energy is enabled. Its macro goals remain unadjusted. Read-only live comparisons with GET /user/goals?date=YYYY-MM-DD confirmed that the widget's energy goal equals the base goal plus activity_energy, while the macro goals are identical in both responses. GET /user/settings confirmed that consume_activity_calories agrees with the widget flag. These diagnostic requests and logs were removed after investigation.

The desktop now subtracts eaten energy directly from the widget's energy goal and uses that same goal for ring progress. Macro targets scale by the adjusted energy goal divided by the base goal (adjusted goal minus included activity). Burned always shows activity_energy, even when inclusion is disabled. The account preference is not changed. Android iz2.t and uef.C separately display burned energy and conditionally include it in the budget; the distinction is also documented at https://help.yazio.com/hc/en-us/articles/360002474498-Why-do-my-calorie-goal-and-nutrient-goals-change.

Product servings supply their conversion amounts in the product's base unit. For example, a public cheese product supplies portion=40 g, slice.small=15 g, and slice=30 g. The picker exposes these alongside the base unit. It retains the exact base amount during unit changes and uses that amount for nutrient previews and writes. A chosen portion also supplies serving and serving_quantity in the consumed-product payload, matching Android vz3's serializer. Tests cover fractional portions, repeated unit changes, liquids, write metadata, and activity inclusion enabled/disabled. No live diary writes were used for verification.

Session-only sign-in and distribution assets — 28 October 2026
Version 2.4.0 replaces the persistent token store with chrome.storage.session, explicitly restricted to TRUSTED_CONTEXTS. Startup deletes the legacy chrome.storage.local tokens entry without reading or importing it. Access/refresh tokens and rotation remain only in the current browser session; there is no persistent alternative. Diary-page refreshes and worker suspension preserve the connection, while Chrome restart or extension reload/update/disable clears it.

All 37 tests pass, including worker restart, browser-session reset, removal of old disk tokens without import, and token capture/refresh without persistent writes. Live Chrome verification confirmed the update requires reconnecting, an existing website session reconnects directly, a diary-page refresh stays connected, and reloading the extension clears the session. The final session was reconnected. The user's browser was not restarted; browser-restart clearing is covered by the documented Chrome API contract and its test model. No live diary or water writes were performed.
